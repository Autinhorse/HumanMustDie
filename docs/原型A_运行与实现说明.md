# 原型 A：灰盒杀戮走廊 — 运行与实现说明

对应设计文档 v0.1 的 §17 里程碑 A 与 §21 首轮实现任务。
引擎 Godot 4.7 + GDScript，数值全部外置在 `data/*.json`。

## 3. 已实现范围

按 §21 的口径，本轮只做灰盒垂直切片：

- **固定走廊地图**：`data/levels/corridor_01.json`，14×20 格，一个入口、一个 2×2 核心、中段一条 2 格宽的窄桥横跨镂空区。
- **格子类型**完全按 §5.3：`0 空地 / 1 普通地面 / 2 墙 / 3 障碍 / 4 桥面 / 5 核心`。
- **入口推导**按确认的规则：地图边缘上离核心最远的那个连通开口（地面或桥面）整段作为出生点，敌人成堆涌入。
- **墙面放置规则**按确认的规则：墙格的四个侧面中，只有正对另一面墙的那一面不可用，其余暴露面（含朝向障碍、朝向空地的面）都能放机关。
- **5 种机关**：地刺、黏胶地面、弹射板、推墙、旋转锯墙。
- **4 类敌人**：小兵（小型）、狂战士（中型）、盾兵（中型、体型更大）、巨魔（重型）。
- **物理**：质量 / 稳定值 / 冲击积累三属性，击飞、滑行、撞墙反弹、落地伤害、坠落处决、被击飞单位撞伤沿途敌人。
- **5 波手工波次**、金币、核心生命、胜负与重开流程。
- **可复现性**：固定步长（1/60）+ 固定种子，战斗日志可导出到 `%APPDATA%\Godot\app_userdata\...\logs\`。
- **统计面板**：分机关的伤害 / 击杀 / 控制秒 / 位移次数 / 连锁击杀，坠落击杀占比，进坑次数，每波准备与战斗用时（文档 §18）。

明确没做（§21 要求排除）：地块抽取与旋转、工程改造、元素系统、自动英雄、局外成长、正式美术。

## 4. 数据配置

改这四个文件就能改玩法，不用碰代码；游戏内 `F5` 热重载。

### `data/config.json`
| 段 | 说明 |
| --- | --- |
| `grid` | 格子边长、墙高、地板厚度与地下支撑长度、格缝 |
| `camera` | 俯角（`pitch_deg`，当前 -45；越小越平，38 最接近参考图但外圈墙会挡住身后一排地格）、朝向、正交可视高度与缩放范围、平移速度、`auto_fit`（载入关卡时自动按地图大小取景）与 `fit_padding` |
| `sim` | 固定步长、每帧最大步数、可选倍速、**随机种子**、`default_level`（启动加载哪个关卡，命令行 `-- --level <id>` 可覆盖） |
| `combat` | 重力、地面摩擦、冲击→速度换算、坠落判定高度、撞击伤害系数与阈值、落地伤害、连锁判定窗口、拥挤分离强度 |
| `economy` | 初始金币、核心生命、清波奖励、拆除返还比例 |
| `entrance` | 入口推导规则 |
| `debug` | 沙盒金币、是否打击杀日志 |

### `data/enemies.json`
`hp` / `speed` / `mass` / `stability`（位移阈值）/ `impact_decay`（每秒冲击衰减）/ `gold` / `core_damage` / `radius` / `height` / `color`。

三档的设计意图：小型 `stability = 0`，任何冲击都直接击飞；中型 18，需要两次推墙或推墙＋弹射板；重型 45，需要五次推墙，且位移速度 = 冲击 ÷ 质量，所以只会短距离滑一段，但滑动过程中会撞伤旁边的小怪。

### `data/traps.json`
每个机关按 §15.3 拆成五段组件，加新机关基本只写 JSON：

```json
"push_wall": {
  "mount": "wall",                       // ground = 地面机关，wall = 墙面机关
  "cost": 100,
  "directional": true,
  "targeting":    { "type": "front_box", "length": 2, "width": 3 },
  "trigger":      { "type": "threshold_count", "min_count": 2, "max_wait": 2.0, "cooldown": 3.0 },
  "payload":      { "damage": 6 },       // 也支持 "dps"（持续触发按 dt 结算）
  "displacement": { "force": 9.0, "up": 0.18 },
  "status":       {}                     // 支持 { "slow": 0.45, "duration": 1.0 }
}
```

现有组件类型：
- `targeting`：`self_cell`、`front_box(length,width)`、`radius(r)`
- `trigger`：`periodic(cooldown,require_enemy)`、`continuous`、`on_enter(cooldown)`、`threshold_count(min_count,max_wait,cooldown)`

加一种新触发/新作用器＝在 `scripts/traps/` 对应文件里加一个 `match` 分支，其余四段不用动。

### `data/levels/*.json`
| 字段 | 说明 |
| --- | --- |
| `grid` | 逐行的格子类型字符串：`0 空地 1 地面 2 墙 3 障碍 4 桥面 5 核心` |
| `entrance` | **敌人从哪进来**。不写就自动推（见下），写了就以写的为准 |
| `allowed_traps` | 这一关工具条上有哪些机关 |
| `waves[].groups[]` | `{enemy, count, interval, delay}` |

**入口怎么定**

不写 `entrance` 时按规则自动推：**地图边缘上离核心最远的那个连通开口**。
所以边缘只留一处开口时最省事，多留几处会互相抢。

要指定就写 `entrance`，支持单格 `"x,y"` 和矩形 `"x,y-x,y"`，可以列多段
（多段就是多个入口，敌人会从所有列出的格子里随机出生）：

```json
"entrance": ["19,14-20,14"]
"entrance": ["5,19", "9,19"]          // 两个各一格的入口
"entrance": [[19, 14], [20, 14]]      // 也支持 [x,y] 数组写法
```

坐标是**格子坐标**，`x` 从左往右、`y` 从上往下，都从 0 开始，和 `grid` 里
字符串的行列一一对应。

写的格子会被校验：不是地面/桥面、或者走不到核心的，会在日志里报出来并忽略；
全都不可用时回退到自动推导。载入日志会写明这一关用的是「关卡指定」还是「自动推导」。

## 5. 代码结构

```

  game.gd              模拟核心：固定步长、波次、经济、放置校验、撞击结算、统计
  enemy.gd             敌人状态机 GROUND / THROWN(含滑行) / FALLING / DEAD

  view/preview.gd      覆盖范围与朝向预览
  ui/hud.gd            界面
  main.gd              相机、输入、放置流程
```

## 6.5 美术风格（v0.0.2 起）

风格参考 `ref/Arrow 05.jpg`（Isle of Arrows）：空中悬浮岛、奶白顶面 + 灰岩侧面、岛底不规则岩体、青灰渐变背景、正交高角、柔和阴影。

所有美术参数集中在 **`data/art.json`**，游戏内按 F5 热重载：

| 段 | 管什么 |
| --- | --- |
| `palette` | 地面顶面（三档随机色差）、侧面、墙、障碍、岩体、核心、入口、云的颜色 |
| `rock` | 岛底岩柱的长度范围、锥度、抖动、随机种子 |
| `clouds` | 薄雾的数量、不透明度、虚化程度、宽度与长宽比 |
| `zoom_readability` | 拉远时的单位放大与地面标记 |
| `environment` | 天空渐变、环境光、色调映射、雾、SSAO、太阳/补光/边缘光、辉光、调色、**屏幕空间描边** |
| `board` | 细缝宽度（设 0 就完全无缝）、面色抬高量、障碍高度、桥面厚度 |
| `anim` | 跑步动作：摆腿/摆臂角度、持剑手臂摆幅比例、躯干与头的前倾、上下起伏、步幅 |

实现上的几个关键点：

- **地面是一整块共面平面**，只靠细缝和颜色分格，不是一格一个凸块 —— 参考图的地表基本是平的。竖直面只在**岛的轮廓**（挨着空地的那一面）生成，墙之间相邻的面也不画，几块墙连成一条完整的墙。
- **`SurfaceTool` 必须 `set_smooth_group(-1)`**：默认走平滑组，会把盒子相邻面的法线平均掉，每块砖看起来都是鼓的，侧面也带弧度。
- **竖直面的顶点绕序必须从底边起**，否则法线朝内，整面会被当成背光面渲染成黑的 —— 表现就是"墙没有侧面，只剩一层薄片"。顶面和侧面的绕序方向是相反的，很容易写反。
- **岛体在地表下面有一段不收缩的实心岩层**（`rock.solid_depth`），再往下才碎成长短不一的石柱。少了这层，岛会变成一张薄片挂着牙齿。石柱的宽度、偏移和有无都随机（`top_scale_min` / `skip_chance`），避免整圈像锯齿。
- **云是背景里的柔边薄雾，不是场景里的 3D 白球**：径向 alpha 渐变的宽扁片，挂在相机上、永远在所有东西后面，和天空只差一点亮度。做成有体积的实心球会硬邦邦地"贴"在画面上，和参考图完全两种东西。
- 整张地图合并成一个带顶点色的 ArrayMesh，一次 draw call。
- **岛底岩体程序化生成**，不是预烘焙模型 —— 里程碑 B 之后地块是随机拼的，岩体必须跟着地图变。桥面下方故意不长岩体（它本来就是没支撑的）。
- **背景是挂在相机上的渐变背板**，不是 Godot 的程序天空：正交相机下所有像素视线方向相同，程序天空会算出一道斜条带瑕疵。
- 顶点色必须声明 `vertex_color_is_srgb = true`，否则 sRGB 值被当线性色用，整张画面发白。
- **环境光遮蔽烘焙进顶点色**（`board.ao_corner` / `ao_side`）：建网格时就按"这个角被几面墙挡住"
  压暗顶点，竖直面越靠下越暗。运行时零开销，对方块地形的立体感提升最大。
- **拉远时的可读性**（`art.json` 的 `zoom_readability`）：正交可视高度越大，敌人在屏幕上
  就越小，拉满时只有几个像素。所以按可视高度做两件补偿 —— 单位模型放大（最多 1.7 倍）、
  脚下淡入一个高饱和的圆形标记。拉近时两者都自动退回去，不影响近景观感。
- **屏幕空间描边**在 `assets/shaders/outline.gdshader`，是挂在相机上的全屏四边形
  （`render_priority = 100`，`depth_test_disabled`）。两个坑：Godot 的 `fragment()`
  里**不能用 `return`**；以及正交相机离场景很远，用"相对深度差"当阈值永远够不到，
  必须用绝对值（世界单位）。
- **全屏后处理绝对不能"读屏幕拷贝再整屏覆盖"**：Godot 的 `hint_screen_texture` 拷贝发生在
  半透明通道之前，拷贝里没有半透明物体，一覆盖就把它们全擦了（地面标记、放置预览、云都
  会消失）。描边改成 `blend_mix` + 只输出线本身（`ALBEDO` 是线色、`ALPHA` 是边缘强度），
  既不需要屏幕拷贝，也不会动到已经画好的内容。

`tools/blender/build_island.py` 读同一份 `data/art.json` 和关卡数据出高质量渲染图（宣传图/风格定稿用），两边配色自动同步：

```
blender --background --python tools/blender/build_island.py -- \n    --project . --level corridor_01 --out renders/island.png
```

游戏内 `F12` 随时截图，存到 `%APPDATA%/Godot/app_userdata\...\shots\`；
调美术时可以让演示场景自动出图：

```
Godot_v4.7-stable_win64.exe --path . res://tests/demo.tscn -- --shot D:/out.png --shot-delay 7
```

## 6.6 从截图转关卡（v0.0.7 起）

`tools/map_from_image.py` 能把地图截图转成我们的关卡 JSON。做法是对图里的颜色做
k-means，按「最蓝 / 最亮的暖色 / 中间暖色 / 最暗」自动分出空地、墙、地面和图外；
再从蓝色块的边界游程自动推出格子间距（相邻档位之差就是间距）和原点；最后每格取
中心区域投票定类型，砖缝的暗色和图标的白色不参与投票。

转 `ref/DungeonWarfareMap01.png` 用的命令：

```
python tools/map_from_image.py --image ref/DungeonWarfareMap01.png     --out data/levels/dw_01.json --name "地牢战争 01（由截图转换）"     --size 26x15 --core 2,3 --core-size 2x2     --wall "9,2-11,4;0,3-0,4" --void "25,3;25,9;10,14"     --entrance "19,14-20,14" --preview renders/dw_preview.png
```

- `--core` / `--core-size`：核心左上角与尺寸（图里的图标识别不了，要手工指定）
- `--wall` / `--void` / `--entrance`：事后修正，`x,y` 或 `x,y-x,y`，分号分隔多段
- `--size` / `--pitch` / `--origin`：不传就自动推；自动结果不对时再手填
- `--pad`：每格采样时四周留多少不采（默认 0.2）。调大能减少邻格污染，但太大会因为
  砖缝的暗色被排除而样本太少、反而更噪

转完会打印**连通性检查**：有多少可行走格、有几格走不到核心、地图边缘有哪些开口。
我们的引擎是按「边缘上离核心最远的连通开口」自动定入口的，所以边缘只留一处开口最省事。

## 6.7 敌人模型与程序化动作（v0.0.9 起）

参考 `ref/swordman.png`，`tools/blender/build_swordman.py` 在 Blender 里用盒子搭出角色
并导出 glb。两种敌人共用同一套骨架：

- `--variant swordman` → `assets/models/swordman.glb`
- `--variant shieldman` → `assets/models/shieldman.glb`，左臂微抬、盾贴在身侧
  （金色边框 + 贯穿上下左右的金色十字），右手照旧持剑。盾兵的上臂用会跟着敌人
  换色的主色（整体是蓝的），剑士才是不参与染色的红袖子

`tools
ebuild_models.bat` 会把两个都生成。**不做骨骼**：每个部件的原点放在关节上
（颈 / 肩 / 髋 / 握把），Godot 里直接给节点转角度就能做动作。

```
Root
 ├ Torso          原点在髋部
 │   ├ Head       原点在颈部
 │   ├ ArmL / ArmR  原点在肩
 │   └ ArmR > Sword 原点在握把
 └ LegL / LegR    原点在髋
```

`scripts/view/actor_view.gd` 负责动作：

- **跑步**由**走过的距离**驱动（不是时间），所以倍速播放时步频自然跟着变，
  减速时也会自动变慢；腿和手臂反相摆动，躯干和头前倾做出俯身冲锋的姿态，
  身体上下起伏。注意**负角才是前倾**：绕 +X 转会把"上"带向 +Z，而角色前方是 -Z。
- 所有动作参数在 `data/art.json` 的 **`anim`** 段，改完 F5 就能试，不用改代码：
  `leg_swing_deg` / `arm_swing_deg`（摆动角度）、`sword_arm_ratio`（持剑那条
  手臂的摆幅比例）、`torso_lean_deg` / `head_lean_deg`（前倾）、`bob_height`
  （上下起伏）、**`stride_ratio`**（步幅占身高的比例 —— 相位由距离驱动，所以
  这个值越大，步子越大、一个跑步循环耗时越长）。
- `anim.per_model.<模型名>` 可以**按模型覆盖**上面任意一项，另外支持 `lock_arms`
  列出哪些手臂保持模型自带的静止姿势不参与摆动。盾兵就是靠这个做的：上身前倾
  只有剑士的一半（7° / 2°），左臂锁住托盾，只有持剑的右臂摆动，腿和剑士一样。
- **被击飞**时缩成一团，比僵直地保持跑步姿势可读。
- **倒地**：先把剑从手上解绑扔出去（自带抛物线和旋转，落地停住），
  身体绕脚跟仰面转 90°，四肢摊平。
- 配色分三类：`armor_primary` 按 `enemies.json` 的 `color` 换；`armor_shade`
  （腿、护手、剑柄）跟着主色但暗一档（暗多少由 `anim.shade_darken` 控制）；
  其余（金色描边、剑刃、面罩、剑士的红袖子）固定不换色。受伤变暗、减速泛蓝
  的逻辑和原来的胶囊一致。

尸体不再参与模拟（不挡路、不吃伤害），播完倒地动画后按 `combat.corpse_life` 清掉；
掉下地图和抵达核心的不留尸体。

**等距相机下的倾角陷阱**：45° 俯视的正交相机会把"往镜头方向倾"的线压扁成近似
水平，所以道具偏离竖直的角度越大，不同朝向看起来差别越大。

- **侧向倾角（绕 Y）必须小**：剑的外倾角一度误设成 45°，表现就是一群小兵里剑
  的朝向五花八门，毫无规律。现在是 8°，只用来让刀身避开上臂。
- **前倾角（绕 X）是刻意的**，目前 30°，配合躯干前倾做出俯身冲锋的感觉。前倾
  会随角色转向一起转，所以"朝镜头跑"和"背对镜头跑"看到的剑角度本来就不同 ——
  这是正常的，因为它始终指向角色的前方，读起来是一致的。
- 手臂摆动时 `actor_view.gd` 会用矩阵把剑锁回静止朝向（`_stabilize_sword`），
  持剑那条手臂的摆幅也降到 55%，否则剑会跟着甩看不清。

**模型调试**：`tests/probe_model.tscn` 会把导入后的节点树、每个节点的静止
位置和朝向打出来 —— 判断"是模型不对还是代码不对"时先跑它，比看渲染图快：

```
Godot_v4.7-stable_win64_console.exe --headless --path . res://tests/probe_model.tscn
```

**朝向约定**：模型在 Blender 里朝 **+Y**（面罩在 +Y 面）。glTF 转 Y-up 后 Blender +Y → Godot -Z，
正好是 Godot 的前方，所以 `enemy.gd` 里用 `atan2(-dx, -dz)` 转向就对。面罩放反了整个人就会倒着跑。

改模型比例改 `build_swordman.py` 里的 `P`，改配色改 `COLORS`，改完跑一次：

```
tools
ebuild_models.bat            双击也行；加 --pose 顺便出姿势检查图
python tools/rebuild_models.py      跨平台的话跑这个
```

**只有改模型才要跑**；改代码、改数值、改关卡都不用。

它做的是两步，第二步不能省 —— **非编辑器模式不会重新导入 glb**，少了它游戏里会一直用旧模型：

```
blender --background --python tools/blender/build_swordman.py --     --out assets/models/swordman.glb --render renders/swordman.png
Godot_v4.7-stable_win64_console.exe --headless --editor --quit --path .
```

Blender / Godot 装在别处的话，设环境变量 `BLENDER_EXE` / `GODOT_EXE`。

动作调完可以用姿势检查场景一次看全（站立 / 跑步两相 / 被击飞 / 倒地两段）：

```
Godot_v4.7-stable_win64.exe --path . res://tests/pose.tscn -- --shot D:/poses.png
      --model shieldman   换模型看（默认 swordman）
      --yaw 90            侧视，判断前倾和剑的倾角必须用它
      --facings           八个朝向排开，检查道具在各朝向是否一致
```

## 7. 已知问题 / 下一步

1. **坠落击杀占比偏高**（示例 57%），正好压在文档 §19 风险二的警戒线上。深坑容量、堵塞、重型豁免都还没实现，建议下一步先加"坑有吞吐上限"再谈平衡。
2. **撞击击杀归属**记在"最后一次给它冲击的机关"名下，所以推墙的击杀数里含撞击连带。这是有意为之（用来评估连锁贡献），但读统计时要知道口径。
3. **击飞撞墙只做速度反射**，没有贴墙滑动；高速斜飞擦到墙角时轨迹会略显生硬。
4. 敌人拥挤用的是逐对分离，密集时有轻微抖动；碰撞检测是 O(n²)，当前波次量级（<60）无压力，上到几百只要换网格分桶。
5. **桥面（类型 4）目前只是"底下没有支撑的地面"**，还没有能打掉它的机关；障碍（类型 3）在本关地图里没用上。
6. 沙盒模式拆除机关不返还金币（避免刷钱），正常模式返还 60%。
7. 界面每帧重建文本，效率不高但对原型无影响。
8. 机关和敌人目前还是配色方块/胶囊，没有真正的模型。下一步应该用 Blender 做**单个道具模型**（机关、核心装饰）导出 glTF——这类固定资产才适合走 Blender，地形部分仍然程序化。
9. 地块系统（里程碑 B）开工前还需要确认：地块之间的接口对齐规则（是否要求接口宽度一致）、三选一候选位置的挑选策略、以及旋转后不可连接时的标红判定细节。
